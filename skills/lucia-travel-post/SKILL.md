## 讀原稿並核對既有文章

按使用者指定的日期、標題與旅程讀完整原稿。來源是 Apple 備忘錄時，優先用已可用的備忘錄工具；沒有專用工具時，透過原生 app 的 UI 讀取。限定在指定內容，保留備忘錄原件，另存原文備份。

以旅程、日期、地點、標題和內文搜尋既有文章。相同旅程已有文章時，更新原檔並保留 slug；確實是不同旅程才新增。來源不完整或日期範圍有歧義時，先完成可確定部分，再詢問缺少資訊。

完成條件：原稿已完整讀取並保留，已決定此次是「新增」還是「更新」，且能指出對應文章。

## 整理文章與地圖

保留 Lucia 的第一人稱、幽默、情緒與旅行細節，整理段落及小標題。英文原稿如有提供，保留在獨立區段。住宿、路線、日期與景點以原稿為依據；新增背景資料時查證並標示來源。

依現有文章格式填寫 frontmatter：`title`、`date`、`description`、`location`、`slug`。`date` 使用旅行日期，保持 `YYYY-MM-DD` 字串；上稿日期與更新日期另行表示。圖片使用使用者提供或已核准的素材，保留來源與必要的說明。

參照 `src/components/MapBackground.tsx` 的現有地圖資料結構，將實際到訪地點連到同一篇遊記。核對座標與地名，保留既有地圖樣式、署名及互動方式。文章需要旅程地圖連結時，使用現有 `/?trip=<slug>` 功能，並確認該 slug 能定位到對應地點。

完成條件：文章標題、日期、摘要與地圖地點一致；每個地點可開啟正確文章；回到旅程地圖時，標記和彈出視窗可閱讀。

## 驗證並依要求發布

在本機檢查文章頁、所有旅誌列表、相關地圖標記及圖片。先閱讀目前 `package.json` 與 `scripts/check-site.mjs`，使用專案現有檢查；程式有變動時，再執行相應的型別、lint 或建置檢查。

發布範圍由使用者當次要求決定：只整理就停在本機；要求上傳 GitHub 就推送本次檔案；要求公開網站或部署 Vercel，就完成部署與公開驗證。載入本 skill 本身不代表同意額外發布內容。

推送前核對差異，僅提交本次工作，保留其他未提交修改。推送後確認遠端分支包含此次提交，才回報 GitHub 已更新。

Vercel 使用原有 `luciaonthego` 專案。先驗證登入與現有 GitHub 自動部署：若相同提交已部署為正式版本，直接驗證公開網站；只有尚未部署時才使用既有發布流程。登入失效時依實際錯誤說明，重新登入後再驗證；需要本人登入時，交給使用者完成。錯誤訊息未交代原因，就把原因標為未知。

完成條件：當次授權的發布階段已完成，且各階段都有實際成功證據。失敗時保留已完成成果，明確指出停在哪一階段。

## 公開列表是必要驗收

以公開網址驗證文章頁、`/posts` 列表、`/api/posts` 及旅程地圖，確認它們包含本次更新。核對 Vercel 正式部署的來源提交與 GitHub 提交。

「所有旅誌」目前依旅行日期由新到舊排序。因此舊年份的新上稿可能在較下面；更新既有文章也不會增加篇數。回報時明確區分「新增文章」與「更新文章」，指出文章在列表的位置，提供可直接閱讀的網址。排序邏輯若日後改變，以實際頁面為準。

使用者說看不到文章時，檢查他指定的公開列表與目前畫面：先確認文章是否真的缺少，再核對排序、捲動位置與部署版本。文章已在列表中時，顯示其位置；需要更醒目的最新更新區時，按使用者要求調整介面，保留真實旅行日期。

最後以簡短繁體中文回報新增或更新的文章、GitHub 與公開網站的實際完成狀態、文章及地圖連結。提供能看到本次成果的公開網站截圖。
